# Routing, telemetry and policy bundles

Status: local/synthetic implementation; no live-provider, payment, Parakh consumer or production rollout has been verified. See ADR-0003. `router_mode=static` and exploration disabled are the defaults. The WhatsApp channel stays disabled.

## Contract and trust boundaries

`docs/contracts/TelemetryBatchV1.schema.json` is Karmi's export contract for Parakh. `docs/contracts/PolicyBundleV1.*.schema.json` describe the JSON documents Parakh must produce; `signature.sig` is base64 Ed25519 over the **raw bytes** of `checksums.json`. `checksums.json` hashes every other included file. Rebuild schemas after model changes with `python scripts/generate_routing_contracts.py`; review schema/version compatibility before publishing. JSON schemas are descriptive, not a substitute for Karmi's verifier (file allowlist, signature, model/feature compatibility, entitlement narrowing and self-tests). A verified bundle cannot override eligibility, accounting or tool permissions. Parakh receives exports and signs candidate bundles; it has no Karmi DB write access. Karmi never trains.

Run with the correct database and policy directory configured via `DAILY_AGENT_*` settings; do not copy keys into tickets/logs. Only authorised operators may set `DAILY_AGENT_ROUTER_POLICY_PUBLIC_KEY` (base64 raw Ed25519 public key). Keep the signing private key outside Karmi. A new key requires a planned rotation: verify/install replacement bundles under the new public key in an isolated environment, test rollback, switch the configured public key together with the compatible store, and retain the prior key/store for rollback. Changing `DAILY_AGENT_AUTH_SECRET` also changes pseudonyms and invalidates existing development tokens; it is **not** a way to re-key historical exports.

## Promotion sequence (do not automate)

1. Record candidate artifact version, Parakh provenance/batch IDs, evaluation/regression evidence, expected entitlements and financial limits. Check that a signed bundle is data-only JSON; do not accept executable files or a private signing key.
2. `python scripts/tasks.py routing verify PATH` and then `python scripts/tasks.py routing install PATH`. A verification failure is terminal for that candidate; investigate the reported rejection code rather than disabling checks.
3. `python scripts/tasks.py routing shadow VERSION`, configure `DAILY_AGENT_ROUTER_MODE=shadow`, and examine `/admin/routing` (admin auth) and telemetry export: live route unchanged, shadow decisions have probabilities, agreement and no shadow model invocation. The default telemetry attribution window is 86,400 seconds; run `python scripts/tasks.py telemetry finalize` after the window, then `python scripts/tasks.py telemetry export --out OUTPUT_DIR`.
4. Confirm regression evidence and real, sufficiently sampled performance/cost/latency results. `python scripts/tasks.py routing mark-good VERSION` after separately validating a known-good candidate. `python scripts/tasks.py routing promote VERSION` requires `passed_regression=true`; changing `state.json` does not affect traffic until `router_mode=bandit` or `canary`. Start with `router_mode=canary` and an approved finite `router_canary_percent`; increase only with measured evidence. Exploration stays off unless explicitly authorised for the allowlisted tiers/domains and bounded by a configured cost ceiling. No fixed exploration percentage is baked into code.
5. Monitor failure/fallback rates, latency and cost in `/admin/routing`, queue/backlog in `/admin/telemetry`, and compare export outcomes against the pre-change baseline. Guardrails only demote; they cannot promote.

## Incident response and rollback

- A bundle rejected on reload or an unreadable state serves eligible static routing; inspect `policy_bundle_rejected`/`policy_state_unreadable` ops events. Shadow errors affect only shadow decisions. A provider circuit opens after configured consecutive failures and excludes that provider until cooldown. If **no** route is eligible, requests defer without a budget reservation; never force a disabled/unentitled model.
- To disable learned routing immediately, set `DAILY_AGENT_ROUTER_MODE=static` in the runtime configuration. To change persistent state use `python scripts/tasks.py routing rollback --reason INCIDENT_CODE`; the store tries verified previous, verified last-known-good, then static. `python scripts/tasks.py routing deactivate --reason INCIDENT_CODE` forces static. Verify `/admin/routing` and a synthetic request after the change. Keep the old artifact and audit state; never edit signed files or `state.json` by hand.
- If telemetry DB writes fail, the non-blocking collector retries and uses the local JSONL spool; check `/admin/telemetry`, disk capacity and filesystem permissions. The spool contains pseudonymous structured events, so protect it like customer telemetry. If disk is also unavailable, telemetry loss is possible; treat that as an operational incident rather than claiming guaranteed delivery. Restore DB first, then replay/verify backlog before exporting. Do not delete the spool to clear an alarm.
- The exporter writes a JSON batch plus `.sha256`; **telemetry export is checksummed, not signed**. It re-validates privacy and fails closed. Validate the checksum and JSON Schema at the Parakh ingest boundary. An export failure must not be bypassed by copying raw rows or sending text for manual repair.
- `python scripts/tasks.py telemetry status` reports unfinalized/unexported backlog. Run `python scripts/tasks.py telemetry finalize`, `python scripts/tasks.py telemetry export`, then `python scripts/tasks.py telemetry purge` to delete **already exported** rows older than `DAILY_AGENT_TELEMETRY_RETENTION_DAYS` (default 90). Preserve unexported rows; coordinate Parakh retention and encrypted backups separately. `purge` is a destructive operator command and needs an approved retention policy/backup before execution.

## Configuration and verification boundaries

The default in-process metrics are per-process and reset on restart; no external metrics backend or fleet aggregation is built. Provider rates and context limits are declared estimates and need provider-side verification before real spend. Local fixtures and mock outages establish software paths only; they do not establish live cost accuracy, provider recovery, real-device behavior or payment/channel eligibility. PostgreSQL/Redis tests require Docker. Production migration/activation, live calls and outbound messages require separate authorisation and observed manual gate evidence. Parakh ingestion cannot be claimed verified unless its separate repository and actual schema consumer are available.
