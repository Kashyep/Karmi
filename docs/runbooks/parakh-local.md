# Offline Karmi <-> Parakh local loop runbook

This runbook documents the reproducible, offline-first feedback loop between Karmi (the daily assistant application) and Parakh (the offline model evaluation and contextual-bandit optimization lab). Every command and output excerpt below comes from a real local loop run on 2026-11-12 (Karmi e49f708, Parakh 6ef18fc; Windows with Python 3.12, LF checkouts), except where marked NOT VERIFIED.

> [!NOTE]
> For cross-repo contract specifications and schema synchronization details, see [docs/contracts/parakh/README.md](../contracts/parakh/README.md).

---

## 1. Purpose and safety box

This runbook exercises the full end-to-end telemetry and bundle loop without network access, live model inference, or external database mutations.

> [!IMPORTANT]
> **Safety guardrails for offline local loops:**
> - **Offline only**: Live providers and integrations are explicitly disabled via environment variables (`DAILY_AGENT_LIVE_MODELS_ENABLED=false`, `DAILY_AGENT_OPENROUTER_ENABLED=false`, `DAILY_AGENT_OPENCODE_ENABLED=false`, `DAILY_AGENT_WHATSAPP_ENABLED=false`, `DAILY_AGENT_PAID_CHECKOUT_ENABLED=false`).
> - **Synthetic data only**: All interactions use synthetic message payloads and synthetic idempotency keys. No customer data or PII is processed.
> - **Local disposable SQLite only**: Karmi and Parakh write strictly to disposable SQLite files located in a temporary directory `$T` outside both repository trees (`sqlite+pysqlite:///$T/karmi.db` and `$T/parakh.db`). Never connect to a hosted or Neon database.
> - **No live provider keys**: No OpenRouter, OpenCode, or beta provider API keys are configured or present in `.env`.
> - **Trusted keys in the local shell only**: `DAILY_AGENT_PARAKH_TRUSTED_PUBLIC_KEYS` is injected directly in the operator's local shell and into the server process. Never commit or persist test keys to shared configuration.
> - **Test-signed policy bundle**: Because Parakh's bundle verifier fails closed when no graded core-benchmark runs exist for real Karmi actions, the shadow leg uses a bundle generated by [`make_karmi_bundle`](../../tests/parakh_helpers.py) and test-signed with an ephemeral local Ed25519 key (not an exported Parakh bundle).
> - **Nothing changes the live route**: Live execution remains pinned to the static baseline (`karmi/fake-economy`). Candidate bundles execute strictly in `SHADOW` mode. Canary and production promotions are deliberately unimplemented in this release.

## 2. Layout and environments

The workflow assumes two sibling checkouts side by side (e.g. `Desktop/Karmi` and `Desktop/Parakh`) with separate virtual environments:

```text
Desktop/
├── Karmi/     # daily-agent application repo
│   └── .venv/ # Karmi Python 3.12 venv
└── Parakh/    # model-lab offline optimization repo
    └── .venv/ # Parakh Python 3.12 venv
```

> [!CAUTION]
> **Never install one repository into the other's virtual environment.** Both repositories contain a top-level `model_lab` package (`src/model_lab` in Karmi and `model_lab` in Parakh). Installing one repo into the other pollutes the namespace and breaks module resolution.

All commands default to Linux/macOS paths (`.venv/bin/python`). For native Windows / WSL equivalents, see [Section 5](#5-windows-and-wsl-considerations).

Set up a disposable scratch directory `$T` outside both repos:
```bash
T=$(mktemp -d /tmp/karmi-loop.XXXXXX)
```

Environment setup:
```bash
# Setup Karmi venv
cd /path/to/Desktop/Karmi
python3.12 -m venv .venv
.venv/bin/python -m pip install -c requirements.lock -e '.[dev]'

# Setup Parakh venv
cd /path/to/Desktop/Parakh
python3.12 -m venv .venv
.venv/bin/python -m pip install -e '.[dev,tui]'
```

## 3. Step-by-step local loop execution

### Step 1: Start Karmi on disposable SQLite

From the `Karmi` repository, launch the API server with live providers disabled and local SQLite storage:

```bash
DAILY_AGENT_ENVIRONMENT=development \

DAILY_AGENT_OPENROUTER_ENABLED=false \
DAILY_AGENT_OPENCODE_ENABLED=false \
DAILY_AGENT_WHATSAPP_ENABLED=false \
DAILY_AGENT_PAID_CHECKOUT_ENABLED=false \
.venv/bin/python -m uvicorn daily_agent.api:app --host 127.0.0.1 --port 8765
```

The server starts up and serves endpoints at `http://127.0.0.1:8765`.

### Step 2: Generate synthetic traffic via HTTP

Send synthetic messages, ratings, and a regeneration request through the HTTP API using `httpx`.

```python
import httpx

client = httpx.Client(base_url="http://127.0.0.1:8765")

# 1. Obtain development bearer token
token_resp = client.post("/dev/token", params={"role": "customer"})
token = token_resp.json()["token"]
headers = {"Authorization": f"Bearer {token}"}

# 2. Post 4 synthetic messages
runs = []
for i in range(4):
    resp = client.post(
        "/v1/messages",
        headers=headers,
        json={
            "text": f"SYNTHETIC: test message {i}",
            "idempotency_key": f"synthetic-w0-{i:03d}",
        },
    )
    runs.append(resp.json())
    # All 4 runs return route "fake-economy" and status "completed"

# 3. Post user feedback: upvote run 0, downvote run 1
client.post(
    f"/v1/runs/{runs[0]['run_id']}/feedback",
    headers=headers,
    json={"rating": "up"},
)
client.post(
    f"/v1/runs/{runs[1]['run_id']}/feedback",
    headers=headers,
    json={"rating": "down", "reason": "unclear"},
)

# 4. Regenerate reply for run 1
client.post(
    f"/v1/runs/{runs[1]['run_id']}/regenerate",
    headers=headers,
    json={
        "text": "SYNTHETIC: test message 1",
        "idempotency_key": "synthetic-w0-regen",
        "reason": "unclear",
    },
)
# Returns 200 OK with previous_run_id pointing to run 1
```

Recorded observation: Traffic completes within time window `[2026-11-12T15:49:15+00:00, 2026-11-12T15:50:16+00:00)`.

### Step 5: Verification fails closed & create test-signed bundle

Testing Parakh's verifier without real benchmark runs demonstrates fail-closed enforcement:

```bash
python -m model_lab verify --db $T/parakh.db --benchmark-runs '{}' pol-29f852d4f7dd69cb0e31
# Exit 2: "--benchmark-runs must be a non-empty JSON object mapping action -> run id"

python -m model_lab verify --db $T/parakh.db --benchmark-runs '{"karmi/fake-economy":"run-does-not-exist"}' --out $T/verify.json pol-29f852d4f7dd69cb0e31
# Exit 2: "unknown run: run-does-not-exist"
```

Because no graded core-benchmark run exists for Karmi's real actions offline, Parakh cannot verify or export an official bundle. The shadow leg therefore uses a **test-signed bundle** built via Karmi's internal helper.

From the `Karmi` repository, generate a disposable Ed25519 test secret and bundle:

```python
import os
import secrets
from pathlib import Path
from daily_agent.parakh import ed25519
from tests.parakh_helpers import make_karmi_bundle

T = Path(os.environ["T"])
keys_dir = T / "keys"
keys_dir.mkdir(parents=True, exist_ok=True)

# Generate a 32-byte Ed25519 test keypair
secret = secrets.token_bytes(32)
(keys_dir / "ed25519.key").write_bytes(secret)
public_key_hex = ed25519.public_key(secret).hex()
print(f"TEST_PUBLIC_KEY={public_key_hex}")

# Generate signed bundle scoring fake-economy 0.1 and system-one 0.9
make_karmi_bundle(
    parent=T / "bundles",
    version="policy-2026.11.12.1",
    bias={"karmi/fake-economy": 0.1, "typesafe/system-one": 0.9},
    secret=secret,
)
```

Save the snippet as `$T/make_bundle.py` (outside the repo) and run it from the Karmi checkout with Karmi's `.venv` and `PYTHONPATH=".:src"`:
```bash
PYTHONPATH=".:src" T="$T" .venv/bin/python "$T/make_bundle.py"
```

### Step 6: Karmi: Receive, stage, and shadow bundle

Configure `DAILY_AGENT_PARAKH_TRUSTED_PUBLIC_KEYS` with the test public key in your local shell session:

### Step 7: Shadow execution and the server restart pitfall

> [!CAUTION]
> **Observed pitfall: the running server must have the trusted key.**
> If the API server was started in Step 1 prior to setting `DAILY_AGENT_PARAKH_TRUSTED_PUBLIC_KEYS`, it cannot verify the shadow bundle. The server silently skips shadow evaluation (requests still succeed) and records `0 shadow decisions`.
> **Remedy:** Restart the uvicorn server with `DAILY_AGENT_PARAKH_TRUSTED_PUBLIC_KEYS` exported in its environment.

After restarting the server with the key, send 3 additional synthetic messages (window `[2026-11-12T15:54:48+00:00, 2026-11-12T15:54:51+00:00)`):

Export telemetry:
```bash
karmi-parakh export-telemetry \
  --start 2026-11-12T15:54:48+00:00 \
  --end 2026-11-12T15:54:51+00:00 \
  --out $T/batch-1.json
```
Output excerpt:
```json
{"batch_id": "karmi-6831916670ff64534e611efd", "runs": 3, "shadow_decisions": 3}
```

Each run records:
- Live decision: `shadow=false`, `action="karmi/fake-economy"`, `probability=1.0`, `policy_version="karmi-static-v1"`.
- Shadow decision: `shadow=true`, `action="karmi/fake-economy"`, `probability=1.0`, `policy_version="policy-2026.11.12.1"`.

Import into Parakh:
```bash
python -m model_lab telemetry import --db $T/parakh.db --source-label karmi-local-w1 $T/batch-1.json
```
Output excerpt:
```json
{"accepted": 3, "quarantined": 0, "observations": 6, "status": "imported"}
```

#### Why no disagreement occurred
Even though the shadow bundle scores `typesafe/system-one` at `0.9` and `karmi/fake-economy` at `0.1`, Karmi's eligible action set offline (with live models disabled) is strictly `["karmi/fake-economy"]` (`routing.eligible_actions`). The shadow policy must select among eligible actions only, so it selects `karmi/fake-economy`. Disagreement requires at least two eligible actions (e.g. an enabled provider), which is out of scope offline.

## 4. Results and key findings

The real local loop run confirmed the following behaviors:

1. **Deterministic telemetry export**: Re-exporting an unchanged timestamp window produces byte-identical `TelemetryBatchV1` files that Parakh imports idempotently (`duplicate` status on re-import).
2. **Server process must hold the trusted key**: Setting `DAILY_AGENT_PARAKH_TRUSTED_PUBLIC_KEYS` in the CLI shell is not enough; the server process running the request pipeline must also have this environment variable. Otherwise the server records 0 shadow decisions and the request still succeeds (no shadow choice, live route unchanged).
3. **No shadow disagreement in offline mode**: Because live models and external providers are turned off, `routing.eligible_actions` filters the candidate set strictly to `["karmi/fake-economy"]`. The shadow policy cannot choose `typesafe/system-one` or any other action, regardless of its internal scoring bias.

## 5. Windows and WSL considerations

For developers on Windows (e.g. `C:\Users\<user>\Desktop\Karmi` and `C:\Users\<user>\Desktop\Parakh`):

- **Recommended: Use WSL.** Ubuntu-24.04 under WSL provides a native Linux environment and avoids POSIX compatibility issues.
- **Git line endings (`core.autocrlf`)**: On native Windows, Git's default `core.autocrlf=true` converts LF line endings to CRLF in signed fixture files and the frozen benchmark file. This causes verification failures (`signature invalid` or `core benchmark changed`). Clone repositories with:
  ```powershell
  git clone --config core.autocrlf=false <repo-url>
  ```
  Or configure globally/locally: `git config core.autocrlf false`.
- **Python paths and separators**:
  - Use `.venv\Scripts\python.exe` instead of `.venv/bin/python`.
  - Use `;` instead of `:` for `PYTHONPATH` (e.g. `$env:PYTHONPATH=".;src"` in PowerShell).
- **Known Parakh test suite failures on native Windows**:
  1. `signal.SIGHUP`: The Parakh TUI references `signal.SIGHUP`, which does not exist on Windows (`AttributeError: module 'signal' has no attribute 'SIGHUP'`).
  2. POSIX file permissions: Tests checking `chmod 0o600` or read-only mode bits on keys fail because Windows NTFS permissions do not map to POSIX mode bits.
- **Stopping stale servers on Windows**:
  ```powershell
  Stop-Process -Id <pid> -Force
  # Find the process listening on the dev port:
  Get-NetTCPConnection -LocalPort 8765 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
  ```

## 6. Parakh Terminal UI (TUI)

The Parakh TUI provides an interactive console for inspecting benchmarks, runs, and datasets.

### Commands
- Launch in demo mode with sample data:
  ```bash
  make PYTHON=.venv/bin/python tui
  ```
  *(Executes `python -m model_lab tui --data lab-data/tui --demo`)*
- Launch against a specific workspace directory:
  ```bash
  python -m model_lab tui --data <directory>
  ```

### CLI options (`python -m model_lab tui --help`)
```text
usage: model-lab tui [-h] [--data DATA] [--suite SUITE] [--demo] [--plan PLAN]

options:
  -h, --help     show this help message and exit
  --data DATA    workspace directory holding model_lab.sqlite3 (default: lab-
                 data/tui)
  --suite SUITE  benchmark suite file (default: benchmarks/seed_cases.jsonl)
  --demo         if the workspace has no runs, start the offline SIMULATED
                 demo on launch
  --plan PLAN    optional pilot plan JSON to preflight (read-only; paid
                 dispatch stays CLI-only)
```

> [!IMPORTANT]
> The `--data` flag expects a **directory** containing `model_lab.sqlite3`, not a path to a `.db` file (from `--help`). NOT VERIFIED: opening the loop database this way was not tried; a possible approach is:
> ```bash
> cp $T/parakh.db $T/model_lab.sqlite3
> python -m model_lab tui --data $T
> ```

> [!WARNING]
> Because `model_lab/tui/app.py` registers a handler for `signal.SIGHUP`, launching the TUI directly on native Windows raises `AttributeError: module 'signal' has no attribute 'SIGHUP'`. Run the TUI inside WSL.
